# 웹훅 인스펙터 PRD

## Executive Summary

웹훅 인스펙터는 백엔드 개발자가 Stripe, GitHub, Slack 등 외부 서비스의 웹훅을 로컬 개발 환경에서 실시간으로 수신·검사·디버깅할 수 있는 백엔드 디버깅 플랫폼이다. 개발자별 고유 수신 URL을 즉시 발급하여 수신된 웹훅 페이로드를 웹 대시보드로 실시간 시각화한다. 핵심 사용자는 외부 웹훅을 활용하는 웹훅 인테그레이션 개발자와 백엔드 팀 리더이다.

## Problem Statement

현업 및 개인 개발 환경에서 Stripe, GitHub, Slack 등 외부 서비스의 웹훅을 활용하는 백엔드 개발자는 로컬 환경(localhost)의 네트워크 방화벽 제약으로 인해 웹훅을 직접 수신하기 어렵다. 외부 서비스는 공인 IP나 도메인을 요구하지만, 개발 중인 로컬 서버는 공인 접근이 불가능하므로 실제 페이로드 구조 파악과 디버깅이 번거롭다.

기존 솔루션(ngrok 등 터널링 도구)은 별도 설치·설정이 필요하고 임시 URL이 세션마다 바뀌어 외부 서비스에 매번 재등록해야 하는 불편이 있다. 또한 수신된 페이로드를 체계적으로 저장·조회하거나, 실패한 전달을 자동으로 재시도하는 기능이 부족하다.

본 프로젝트는 개발자별 영구 수신 URL을 발급하고, 수신된 웹훅을 실시간 대시보드로 시각화하는 엔터프라이즈급 인프라를 AWS 기반으로 구현한다. 사용자 인증은 Supabase Auth에 위임하여 인증 인프라 운영 부담을 최소화한다.

## Target Users

### 웹훅 인테그레이션 개발자

Stripe, GitHub, Slack 등 외부 서비스와의 웹훅 연동 기능을 개발하는 개인 또는 소규모 팀의 개발자. 로컬 개발 환경에서 웹훅 페이로드를 직접 확인하고 로직 테스트를 반복해야 한다. 고유 수신 URL 발급과 실시간 시각화 기능을 주로 활용한다.

### 백엔드 팀 리더

2~5인 백엔드 팀을 이끄는 시니어 개발자 또는 테크 리드. 팀원들의 웹훅 인테그레이션 작업을 감독하고 장애 발생 시 로그를 분석한다. CloudWatch 모니터링 대시보드를 통해 수신 트래픽과 시스템 상태를 관리한다.

## User Stories

- US-001: As a 웹훅 인테그레이션 개발자, I want 계정 생성 후 첫 로그인 시 고유한 웹훅 수신 URL을 발급받기를 원한다 so that 외부 서비스에 해당 URL을 등록하고 즉시 테스트를 시작할 수 있다.

- US-002: As a 웹훅 인테그레이션 개발자, I want 수신된 웹훅의 헤더와 페이로드를 웹 대시보드에서 실시간으로 확인하기를 원한다 so that 외부 서비스가 어떤 데이터 구조로 요청을 보내는지 코드 작성 전에 파악할 수 있다.

- US-003: As a 백엔드 팀 리더, I want 초당 웹훅 수신량과 시스템 지연시간을 모니터링하기를 원한다 so that 트래픽 폭증 시 병목 구간을 빠르게 파악하고 대응할 수 있다.

## Functional Requirements

### FR-001: 고유 웹훅 수신 URL 발급

사용자가 서비스에 가입(Supabase Auth)한 후 첫 로그인 시 고유한 웹훅 수신 엔드포인트 URL이 자동으로 발급되며, 해당 URL로 전송된 모든 HTTP 요청이 수신된다.

**Acceptance Criteria:**
- Supabase Auth로 회원가입·로그인 처리
- 첫 로그인 후 `GET /v1/webhook-url` 호출 시 즉시 고유 URL 발급 (형식: `https://hook.example.com/{uuid}`)
- HTTP POST 메서드의 모든 Content-Type 수신 지원 (application/json, form-data, text/plain)
- 동일 URL로의 연속 요청 수신 시 순서 보장
- URL 비활성화 옵션 제공 (비활성 URL로의 요청은 4xx 응답)

### FR-002: 수신 웹훅 실시간 대시보드 시각화

수신된 웹훅 이벤트가 브라우저 새로고침 없이 1초 이내에 웹 대시보드에 표시된다.

**Acceptance Criteria:**
- 수신 즉시 WebSocket(STOMP)으로 브라우저에 Push
- 표시 항목: 수신 시각, HTTP 메서드, 경로, 헤더 전체, 페이로드(JSON Pretty Print)
- 과거 웹훅 이력 조회 (최근 1,000건)
- 특정 웹훅 선택 시 상세 페이로드 확인 가능

## Non-Functional Requirements

- NFR-001: AWS 관리형 서비스 기반 아키텍처 준수 — EC2(Auto Scaling), ALB, SQS, DynamoDB 등 AWS 관리형 서비스 3개 이상을 조합하여 운영 부담을 최소화해야 한다. 사용자 인증은 Supabase Auth에 위임하여 인증 인프라 운영 부담을 제거한다. 2인 팀이 인프라 관리 부담 없이 운영 가능한 수준이어야 한다.
- NFR-002: 실시간 통신 지연 1초 이내 — 웹훅 수신 후 대시보드 표시까지 P95 기준 1초 이내여야 한다. Spring WebSocket(STOMP)을 통해 구현한다.
- NFR-003: 트래픽 폭증 대응 — SQS 비동기 처리로 초당 100건 이상의 웹훅 수신에 대응할 수 있어야 한다. EC2 Auto Scaling Group(t3.micro)으로 처리량 자동 확장 (스파이크 발생 후 60초 이내 정상 복귀, 오류율 5% 미만).
- NFR-004: 데이터 내구성 99.99% — DynamoDB에 저장된 웹훅 데이터는 99.99% 내구성을 보장해야 한다. 저장 중 데이터 손실 없음.
- NFR-005: 보안 인증 — 각 사용자의 웹훅 URL은 타인이 추측할 수 없는 UUID v4 기반이어야 한다. API 인증은 Supabase Auth가 발급한 JWT(HS256)를 백엔드에서 검증하며, TLS 1.2 이상으로 통신을 암호화한다.
- NFR-006: 운영 모니터링 — AWS CloudWatch와 CloudWatch Agent를 통해 초당 수신량, EC2 CPU·메모리, 처리 지연 등 핵심 지표를 시각화하는 운영 대시보드를 구축한다.

## Out of Scope

- 모바일 앱 (웹 브라우저 대시보드만 제공, 모바일 전용 앱 개발 없음)
- 결제 및 과금 기능 (MVP는 무료, 과금 모델 설계 없음)
- AWS 이외 클라우드 인프라 지원 (GCP, Azure 등 멀티클라우드 대응 없음)
- 채팅 또는 협업 기능 (팀원 간 실시간 협업 기능 없음)
- 웹훅 이외 프로토콜 지원 (gRPC, MQTT 등 비HTTP 프로토콜 없음)
- 목적지 서버 포워딩 (수신된 웹훅을 사용자 지정 서버로 중계하는 기능은 현재 범위에서 제외; 향후 확장 기능으로 고려)
- 자체 인증 시스템 구축 (Supabase Auth 사용; 자체 회원가입·로그인·비밀번호 관리 로직 구현 없음)
- IaC 도구 (AWS CDK·Terraform 등 미사용, AWS 콘솔 직접 세팅)

## Future Extensibility

아래 기능은 현재 범위에 포함하지 않으나, 아키텍처 확장 시점에 도입 가능한 항목으로 명시한다.

- **사용자 지정 목적지 포워딩:** 수신된 웹훅을 사용자가 등록한 외부 서버 URL로 중계(Relay)하는 기능. 조건부 포워딩, 지수적 백오프 재시도, DLQ 기반 실패 격리 및 수동 Replay를 포함한다. RelayService와 DestinationService 컴포넌트를 추가하고 SQS retry queue 및 DLQ를 도입하면 현재 아키텍처와 독립적으로 붙일 수 있다.
- **IaC 도입:** 인프라 규모 확장 시점에 AWS CDK 또는 Terraform으로 현재 콘솔 설정을 코드화.

## Success Metrics

- 웹훅 수신 후 대시보드 실시간 표시 지연 P95 기준 1초 이내 달성
- 웹훅 수신 후 DynamoDB 저장까지 전체 처리 지연 P95 기준 3초 이내
- 월간 서비스 가용성 99.9% 이상 (월 downtime 44분 이내)
